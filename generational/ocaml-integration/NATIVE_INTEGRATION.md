# Integrating the verified generational GC into OCaml 4.14

What had to be done to make OCaml run on the verified collector, for both
flavours — bytecode (`ocamlrun`) and native (`libasmrun.a`) — and what is still
missing. Organised by the thing being integrated rather than by the order it was
discovered; the bug table in §3 is the index into the interesting failures.

**Status.** Both flavours work well enough to bootstrap the compiler. `make
coldstart`, `make core`, `make opt-core` and `make world.opt` all complete, and
`make bootstrap` reaches a fixpoint — a compiler compiled by itself, under the
verified GC, reproducing its own bytecode sections across three self-hosting
generations. The OCaml testsuite passes 2910–2921 of 3141 considered test
instances; the residue is dominated by two unimplemented subsystems (§5). Two
soundness fixes live in hand patches on proof-extracted code rather than in the
F\* source (§2.7, §5). Two environment-dependent crashes remain open (§7).

---

## 1. The shape of the problem

The verified collector is written in F\*/Pulse, extracted to C
(`generational/snapshot/GC_Gen_Impl.c`), and joined to OCaml's runtime by a
hand-written bridge, `verified_gc/alloc_gen.c`. The bridge exists because the two
sides describe memory differently: OCaml speaks in absolute addresses and
domain-state fields, the verified code in 0-based offsets over its own
structures.

The persistent difficulty is that OCaml has **two runtimes with opposite
conventions**, and the collector has to serve both:

| | bytecode (`ocamlrun`) | native (`libasmrun.a`) |
|---|---|---|
| who allocates | a patched macro calling into the bridge | instructions the compiler emits inline |
| authoritative state | `bump_ref`, counting **up** from 0 | `young_ptr`, counting **down** from the top |
| nursery filled from | the low end | the high end |
| `young_ptr` | parked at `young_alloc_end`, never moves | the real allocation pointer |
| reaches our C code per allocation | yes | **no** — only on a trap |

Nearly every bug below is a consequence of that table: something true of one
flavour was assumed of the other, or a value meaningful in one convention was
handed to code reading it in the other.

## 2. What had to be done

### 2.1 Build plumbing

The verified collector compiles to two archives, `libvergc_gen.a` (bytecode) and
`libvergc_gen_native.a` (native), from the committed snapshot — no F\* toolchain
is needed to build the OCaml side.

Both OCaml runtime archives must **embed** those objects, because the patched
`interp.c`/`memory.h` reference `vergc_minor_base`, `vergc_minor_bump_ref`,
`vergc_minor_size` and `verified_allocate_minor`:

- `libasmrun.a` extracts `libvergc_gen_native.a` into itself.
- `libcamlrun.a` does the same with `libvergc_gen.a`.

`libcamlrun.a` originally did not. `ocamlrun` links both archives explicitly so
it worked, which hid the problem: every `ocamlc -custom` link sees only
`libcamlrun.a` and failed with undefined references. That breaks any
`-custom` user program, and it blocked `ocamltest` — which builds a custom
runtime — so the testsuite could not be run at all.

### 2.2 Domain-state layout — the subtle one

`utils/domainstate.ml`, which the **native code generator** uses to compute byte
offsets for `young_limit`/`young_ptr`, is generated by preprocessing
`runtime/caml/domain_state.tbl`. An early version of the patch inserted a new
field before `young_limit`:

```
+DOMAIN_STATE(value, temp)
 DOMAIN_STATE(value*, young_limit)
 DOMAIN_STATE(value*, young_ptr)
```

shifting every later field by one slot. But test programs are compiled by
`ocamlopt` from the *unchanged* tree, built from the *stock* table. So the
compiler emitted `cmpq Caml_state(young_limit), %r15` using stock offsets while
the runtime had `temp` there — every native allocation compared `young_ptr`
against an unrelated scratch word, and `caml_call_gc`'s save/restore of
`young_ptr` was one slot off, corrupting the register-save path that every
native trap goes through. Measured symptom: a 24-byte allocation trapping with
2 MB free and only 192 bytes used since the last reset.

**Resolution:** never change the struct layout. The bridge uses
`extra_params[0]` — a 64-word array already reserved in stock's own
`domain_state.tbl` for exactly this kind of extension. No new field, no compiler
rebuild, and native's layout stays byte-identical to stock's.

The lesson generalises: anything that changes a structure the *unmodified*
compiler also has offsets for is a layout ABI break, not a local edit.

### 2.3 Startup wiring

`ensure_heap()` allocates the major and minor heaps, initialises the verified
structures, and points the domain state at our nursery
(`young_start`/`young_end`/`young_alloc_start`/`young_alloc_end`). It also, and
this is load-bearing:

- **re-derives both trigger fields** against the buffer just installed.
  `caml_init_gc()` set `young_trigger` and `caml_memprof_young_trigger` relative
  to the stock buffer we then replace, and `caml_update_young_limit()` takes the
  max of the two as `young_limit`. `caml_memprof_renew_minor_sample()` is the
  correct single entry point (it calls `caml_update_young_limit()` itself, so it
  must come *after* `young_trigger` is set). Getting this wrong made memprof's
  sampling callback fire on every allocation in a program that never started
  memprof, and later tripped the debug runtime's assertion at `signals.c:232`.
- **registers both heaps in the page table** — `In_heap` for the major heap so
  `Is_in_heap()` is true and the write barrier records inter-generational
  pointers, `In_young` for the nursery so `Is_young()` works.

Native additionally needs `vergc_native_minor_startup_init()`, called from
`startup_nat.c` right after `caml_init_gc()`, because native's compiled fast path
never enters our C code — nothing would trigger the lazy `ensure_heap()` that
bytecode gets on its first allocation. It also sets `young_trigger`/`young_limit`
and frees the stock buffer `caml_init_gc()` had just allocated, which would
otherwise leak 2 MB per process.

### 2.4 Allocation paths

`Alloc_small_aux` (`runtime/caml/memory.h`) is flavour-split, and the split
matters:

- **bytecode** allocates through a hand-written inline fast path in the macro
  itself, *not* through the verified allocator. It reimplements bump allocation
  in C — bounds check, pointer computation, bump of `vergc_minor_bump_ref`, and
  writing the header — and only falls back to `verified_allocate_minor()`
  (which does call the verified `minor_alloc()`) when the nursery is full. The
  slow path is wrapped in `Setup_for_gc`/`Restore_after_gc` so the interpreter's
  `sp` and `accu` are visible to the root scan.

  Be precise about what that means for the trust story: the fast path is taken
  for essentially every bytecode allocation, and the verified `minor_alloc()`
  runs roughly once per nursery-full event. **The hot allocation path in
  bytecode is unverified hand-written C**, sharing only the `bump_ref` variable
  with the verified allocator. See `../PATCHES.md` B15.
- **native** uses genuinely stock allocation against the real
  `young_ptr`/`young_limit`. Redirecting it into the bridge's bump allocation
  would create two disjoint nurseries in one process, which `Is_young()` cannot
  reconcile. (This was found the hard way — see "cross-contamination" in the bug
  table.)

Consequence worth remembering: in native, `verified_allocate_minor()` and
`minor_alloc()` are never called. The verified minor *allocator* is
bytecode-only; for native the nursery is purely a collection input.

And this is permanent, not a gap to be closed. Native's allocation is emitted by
`ocamlopt`'s amd64 backend for `Ialloc` — subtract from `%r15`, compare against
`young_limit`, branch to `caml_call_gc`, write the header inline — and enters
runtime code only on the trap. It cannot call *any* allocator of ours. Verifying
it would mean verifying OCaml's code generator, a different project entirely.

The useful thing to do instead is state its contract explicitly — `young_ptr`
descends from `young_alloc_end`, traps when it falls below `young_limit`, writes
a well-formed header — and make the collector's proofs depend on that as a
*written* assumption. `well_formed_heap` should have been doing exactly that for
infix blocks and was not (§2.7), which is how an unexamined assumption became
silent corruption.

### 2.5 Trap redirection

Every path that wants "empty the nursery" must reach our collector, never
stock's semispace body. They are funnelled through one bridge entry point,
`vergc_run_minor_collection()`:

| caller | why it matters |
|---|---|
| `caml_empty_minor_heap()` | the shared definition behind `caml_gc_dispatch()`, memprof, every `Gc.*` entry point in `gc_ctrl.c`, and `compact.c` |
| `caml_minor_collection()` | `caml_make_vect()` calls it to *establish* that a young `init` was promoted, then fills a major array with plain stores, deliberately skipping `caml_initialize` |
| `caml_alloc_small_dispatch()` | the one site both the native compiled-code trap and plain C helpers (`custom.c`, `weak.c`) funnel through |

Redirecting individual call sites is whack-a-mole — memprof's direct call was
missed once. Redirecting the shared definitions covers current and future
callers by construction, and stock's semispace body is `#if 0`'d so nothing can
reach it even by accident.

Two traps for the unwary here:

- A **stub is not a safe default.** Both `caml_minor_collection()` and
  `caml_empty_minor_heap()` were once no-ops "because we have our own
  collector"; callers that use them to establish facts then acted on false
  premises.
- Stock's `caml_empty_minor_heap()` body *looks* harmless in bytecode because
  its `young_ptr != young_alloc_end` guard reads "already empty" — bytecode
  parks `young_ptr` there. It silently did nothing while looking like working
  code, which is worse than an obvious stub.

`caml_check_urgent_gc()` now routes here too. It had been stubbed, and the
stated reason ("it would introduce new collection points") was wrong twice
over. These are *safe* points by construction: callers pass their live value
through the function (`result = caml_check_urgent_gc(result)`) or call it inside
a `CAMLparam`/`CAMLreturn` block, precisely so the value is registered as a root
and updated across a moving collection — stock's collector promotes objects here
too.

The real hazard is narrower: stock services the request via
`caml_gc_dispatch()`, which runs `caml_major_collection_slice()` — stock's
*incremental major* GC, which knows nothing about our heap. If it ran,
`caml_gc_phase` would leave `Phase_idle` and `caml_modify` would begin calling
stock's `caml_darken` on our objects. So we call our collector directly and
never go through `caml_gc_dispatch()`.

What the stub had been costing: the request is mostly set by
`realloc_generic_table()` when the remembered set hits its threshold — a "drain
me" signal. Unserviced, `ref_table` doubled instead, growing far larger between
collections than stock would allow. Not a correctness bug, but a silent
divergence with no reason behind it.

### 2.6 The `young_ptr` ↔ `bump_ref` translation

Native's authoritative state is `young_ptr`; the verified collector's is
`bump_ref`. `vergc_sync_bump_from_young_ptr()` publishes one as the other:

```c
used_bytes = young_alloc_end - young_ptr;
if (used_bytes > minor_heap_size_u64) used_bytes = minor_heap_size_u64;
*bump_ref = used_bytes;
```

The directions differ but **the count does not** — this is the identity on
"bytes in use", not its complement. The clamp covers native decrementing
`young_ptr` before its bounds check, so on a trap it can legitimately sit below
`young_alloc_start` until `caml_alloc_small_dispatch`'s undo step runs.

It is called from `vergc_native_run_minor_collection()` and from the top of
`do_full_gc()`, because a full GC can be entered without passing through the
minor path (`verified_allocate()` runs one when a major allocation needs space).

`verified_gc/spike_young_ptr_invariant.c` is a standalone emulation of this dance
— 200,000 allocations over a 4 KB buffer, asserting `young_ptr == result - 8`
after every trap and no overlap between epochs. It caught a real bug (missing the
`young_ptr += whsize` undo before computing `used_bytes`). Note it cannot catch
the complement error: its only assertion on the value is `bump_ref <= HEAP_SIZE`,
true either way, and its stand-in collector never reads `bump_ref`.

### 2.7 Infix pointers

OCaml allocates mutually recursive closures as **one block**, with the second and
later functions referenced by pointers into its middle, just past an
`Infix_tag` (249) header whose size field records the offset back to the start.
This is the only place OCaml deliberately creates a pointer that does not aim at
an object's beginning, and both collectors must handle it:

- **major mark**: darkening a pointer must first normalise an infix pointer to
  its enclosing closure, exactly as stock `caml_darken` does with
  `v -= Infix_offset_val(v)`. Without it, a closure reachable only via infix
  pointers stays white and is swept while live.
- **minor promote**: deciding "this word is an infix header" from `tag == 249`
  alone is **unsound**. `Infix_tag` is odd by design so that an infix header read
  as a value looks like an integer — which means some integers, read as headers,
  look like infix tags. Both sites must additionally require the implied parent
  to be a real `Closure_tag` block, per `mlvalues.h`: *"infix headers can only
  occur in blocks with tag Closure_tag"*.

Both fixes are **hand patches on extracted code** (patches 14 and 15 in
`../PATCHES.md`), because `well_formed_heap_part4`
(`common/spec/GC.Spec.Fields.fst:694`) asserts that no object is infix. The
proofs are sound; the precondition is simply false for real OCaml heaps, and
nothing checks it at the bridge boundary — so a false hypothesis degraded into
silent corruption instead of a failed proof. `PATCHES.md` has the details and the
elimination plan.

### 2.8 Keeping the hand patches alive

`make snapshot` overwrites `snapshot/` with a plain `cp` from `_extract/`, so
hand edits were silently dropped on every regeneration. They are now kept as
patch files and re-applied by the snapshot target:

```
generational/patches/snapshot/*.patch          the patches
make -C generational snapshot                  extract -> cp -> apply
make -C generational apply-snapshot-patches    idempotent; hard error on conflict
make -C generational verify-snapshot-patches   assert they are present (CI)
```

Failing loudly on conflict is the point: the alternative is a snapshot that
quietly lacks a soundness fix.

## 3. Bugs found, and what each one taught

| # | Bug | Symptom | Lesson |
|---|-----|---------|--------|
| 1 | `Alloc_small_aux` redirected native allocation into the bridge's bump path | two disjoint nurseries in one process | `Is_young()` cannot reconcile two nurseries; native must use stock allocation |
| 2 | Domain-state layout shifted by a new `temp` field | every native allocation compared `young_ptr` against a scratch word | changing a struct the unmodified compiler has offsets for is an ABI break |
| 3 | Stale `caml_memprof_young_trigger` | memprof sampling fired on every allocation; debug-runtime assertion | trigger fields must be re-derived against the installed buffer |
| 4 | Stock's minor buffer never freed | 2 MB leak per native process | if you replace an allocation, reclaim the original |
| 5 | Only `caml_garbage_collection` redirected | plain C helpers reached stock's collector, desyncing `young_ptr` from `bump_ref` | redirect shared definitions, not call sites |
| 6 | `bump_ref = size - used` instead of `used` | whole young generation silently discarded when the nursery ended exactly full; appeared to depend on the executable's *filename* | a direction change is not a complement |
| 7 | `caml_minor_collection()` a no-op stub | `Array.make` produced arrays of dangling pointers (20000 fields, 17 ref_table slots) | callers use collections to establish facts they then rely on |
| 8 | Bytecode ran stock's `caml_empty_minor_heap` | every "drain the nursery" request silently did nothing | a guard that reads "already empty" is worse than a stub |
| 9 | Major darken did not normalise infix pointers | live closures swept; NULL code pointer in the interpreter | see §2.7 |
| 10 | Infix detected by a bare `tag == 249` | `Val_long(1788)` = `0xdf9` taken for an infix header; a ~1 TB allocation request reported as "major heap full" | a tag test needs the word to *be* a header |
| 11 | `libcamlrun.a` missing the verified objects | all `-custom` links failed; testsuite unrunnable | both runtime archives need the same treatment |

Bugs 9 and 10 interact: while 9 was destroying live closures, the minor
collector never had to promote surviving infix structure, so 10 was unreachable.
Fixing 9 exposed 10. Measured by toggling the fix: `translattribute.ml` compiles
3/3 without patch 14 and fails 3/3 with it.

Bug 10 also explains a misdiagnosis worth guarding against: `new_parent_addr ==
0` conflates genuine allocator exhaustion, a zero size, and a nonsense size
request, reporting all three as "major heap full". That sent three builds chasing
`MIN_EXPANSION_WORDSIZE`.

## 4. How it is verified

Ordered by strength.

**Smoke tests.** `make -C tests test` (bytecode) and `test-native` — eight
benchmarks, same programs and arguments in both flavours, kept in lockstep on
purpose.

**The compiler bootstrap.** Far more demanding than any benchmark: hundreds of
processes, real allocation patterns, and self-checking.

| target | what it builds |
|---|---|
| `make coldstart` | the stdlib, via `boot/ocamlc` |
| `make core` | `ocamlc`, ocamllex, tools, library |
| `make opt-core` | `ocamlopt` + the native stdlib |
| `make world.opt` | `ocamlc.opt`/`ocamlopt.opt` — the compilers themselves as native binaries |

`Makefile.common` defaults `OCAMLRUN` to `boot/ocamlrun`, and `coldstart` copies
`runtime/ocamlrun` over it, so every compiler invocation runs on the verified GC.
The `.opt` binaries link `libasmrun.a`, so they *run on* the collector rather
than merely emitting code for it.

**Differential compilation** — the sharpest correctness check available short of
a proof. Compiling the same modules with the same `boot/ocamlc` under our runtime
versus stock produced **byte-identical** `.cmo` output for 8 of the compiler's
own modules, including `parsing/parser.ml`, `typing/typecore.ml` and
`lambda/matching.ml`.

**The bootstrap fixpoint.** `make bootstrap` promotes our compiler over
`boot/ocamlc`, rebuilds with it, promotes again, rebuilds the core system, and
requires generations *N* and *N+1* to agree: `Fixpoint reached, bootstrap
succeeded.` Note `cmpbyt` compares bytecode *sections*, not whole files — the
files differ because `promote` runs `tools/stripdebug`. So the claim is that the
compiled code and data are identical across three self-hosting generations, not
that the containers are byte-identical.

Caveat: plain `make compare` fails against the *upstream-shipped* `boot/ocamlc`,
which was never built from this tree — and it fails identically in the unchanged
tree, so that is a property of the release tree, not a miscompilation.

**The OCaml testsuite.** `make -C testsuite all` after `make world.opt` and `make
ocamltest`; 231 directories, ~3100 test instances, both flavours in one run.
Requires `ocamltest`, which needs the `libcamlrun.a` fix (§2.1). Automated by
`.github/workflows/testsuite.yml`, gated on *no new failures* against
`ci/expected-failures.txt` rather than on zero failures, since a permanently-red
check stops being read. `ci/testsuite_report.py` emits an HTML report and buckets
failures by cause.

Against stock through the identical suite:

| | stock | verified GC |
|---|---|---|
| passed | 2985 | 2910–2921 |
| failed | 0 | 28 |
| unexpected errors | 0 | 43 |
| considered | 3141 | 3141 |

Stock is clean, so every failure is attributable rather than environmental.

**A gotcha that costs a run:** `make bootstrap` ends with `partialclean` + `core`,
which removes `ocamlopt`. The testsuite's support library needs it, so re-run
`make world.opt` afterwards or you get `cannot find file '../../ocamlopt'`.

## 5. Known limitations

**No ephemerons, weak references, or finalisers.** The bridge processes
`ref_table` only — never `ephe_ref_table`, `custom_table`, or
`caml_final_update_minor_roots()`. A weak array is `Abstract_tag`, so the
collector neither traces **nor clears** it: stock's major GC clears weak pointers
whose target died, while we sweep the target and leave the array pointing at a
freed block, so `Weak.get` returns `Some <dangling>`. This accounts for ~25 of
the testsuite failures. Measured as *not* involved in the bootstrap:
`ephe_list_head` was empty across all 65 collections of a failing stdlib compile,
and no compiler source, tool, or ocamldoc file uses `Weak`/`Ephemeron`/
`Gc.finalise`.

**The bytecode hot allocation path is unverified.** `Alloc_small_aux`'s inline
fast path (`runtime/caml/memory.h`) is hand-written C that bumps
`vergc_minor_bump_ref` and writes the header directly; the verified
`minor_alloc()` is reached only via the slow path, i.e. about once per
nursery-full event. So "bytecode runs on the verified allocator" is false as
stated — it runs on an unverified reimplementation that shares the verified
allocator's state variable. Catalogued as B15 in `../PATCHES.md`.

**No statistical memory profiling.** `ensure_heap()` parks
`caml_memprof_young_trigger` and never arms sampling. ~24 testsuite failures.

**Fixed, non-expanding major heap, no compaction.** Sized by
`MIN_EXPANSION_WORDSIZE` (default 32M words = 256 MB), and fragmentation is
never recovered. Exhaustion now raises a catchable `Out_of_memory` from the
allocation path, with a one-time stderr hint naming the knob — it used to abort
the process, because `verified_allocate()` called `caml_fatal_error()` and
`caml_alloc_shr_aux()` had lost stock's `wosize > Max_wosize` and NULL guards,
so `check_oom()` never received the 0 it needed. Exhaustion detected *during
promotion* is still fatal, and correctly so: you cannot raise mid-collection,
which is the same distinction stock's own `check_oom()` makes via
`Caml_state->in_minor_collection`.

**Two soundness fixes are unverified.** Patches 14 and 15 edit proof-extracted C
and are outside every proof. `make snapshot` re-applies them (§2.8), but they
remain unverified code in files that are supposed to be proof output.

**Testsuite coverage of infix is thin.** Only `lib-marshal/intext.ml` ("Test for
infix pointers") targets it directly, and it passes. `misc/ephe_infix*.ml` are
ephemeron tests that merely *use* infix values, so they are gated behind the
missing weak support and prove nothing about infix. The real infix exercise is
the bootstrap, which is incidental rather than targeted — a dedicated stress test
(closures reachable only via infix, surviving several major cycles, salted with
integers whose low byte is `0xf9`) is still worth writing.

## 6. Reproducers

Compile with the **stock** `ocamlc`, run under both runtimes, with
`MIN_EXPANSION_WORDSIZE=33554432`. A small heap gives a legitimate "promotion
failed — major heap full", which is a clean error rather than a bug.

```ocaml
(* the minimal bug-7 reproducer: no closures involved *)
let () =
  let keep = Array.init 20000 (fun i -> (i, i+1, string_of_int i)) in
  for _ = 1 to 300 do ignore (Array.make 20000 0) done;
  let acc = ref 0 in
  Array.iter (fun (a,b,s) -> acc := !acc + a + b + String.length s) keep;
  Printf.printf "ok %d\n" !acc
```

```ocaml
(* one explicit full GC is enough *)
let () =
  let keep = Array.init 1000 (fun i -> (i, string_of_int i)) in
  Gc.full_major ();
  let acc = ref 0 in
  Array.iter (fun (i, s) -> acc := !acc + i + String.length s) keep;
  Printf.printf "ok one-gc %d\n" !acc
```

```ocaml
(* control: immediates, no pointer children. Always passed. *)
let () =
  let keep = Array.init 20000 (fun i -> i) in
  for _ = 1 to 300 do ignore (Array.make 20000 0) done;
  let acc = ref 0 in Array.iter (fun i -> acc := !acc + i) keep;
  Printf.printf "ok int-array %d\n" !acc
```

The discriminating triple that localised bug 7: immediates always passed, churn
with no live data always passed, live data never read back always passed — only
*reading pointer children back* crashed.

### The diagnostic that found bugs 9 and 10

Three cruder checks reported the post-collection heap clean, because each asked
"is the target's header blue (free)?". Once a swept block is **coalesced** into a
larger free block its old address is interior, so the word at `target - 8` is
stale data (observed `0x0`), not a blue header. The check that works builds a
bitmap of live block *starts* from a linear heap walk and requires every pointer
in every live object to hit one — with infix pointers special-cased, or it
produces false positives (its first run flagged 40 "dangling" roots that were all
legitimate infix pointers into live closures).

That check found 53 fields of live objects pointing into freed, coalesced blocks.
It is worth re-adding, env-gated, whenever this area is touched.

## 7. Open work

**Two environment-dependent crashes.** Both appear on GitHub's Ubuntu 24.04
runners and neither reproduces locally (0/30 on Fedora/glibc 2.43, 0/25 in an
Ubuntu 24.04 container sharing the host kernel, so glibc is exonerated):

1. **Bytecode.** `ocamlrun` running `ocamlopt` segfaults during `opt.opt`, ~50%
   of runs, at a different compilation unit each time (`tast_mapper.cmx`,
   `ast_helper.cmx`).
2. **Native.** `tests/ast-invariants/test.ml` compiles fine, then the resulting
   *native binary* dies on signal 11. Notably this is the one test in 3141 that
   flipped to passing when patch 14 was hardened, which makes the infix darkening
   path the first place to look.

Ruled out for these: glibc version; stock's incremental major GC leaking in
(`caml_alloc_small_dispatch` is reachable only from `signals_nat.c` and the
native `Alloc_small_aux`, so in bytecode `caml_gc_phase` never leaves
`Phase_idle` and `caml_modify`'s stock-`caml_darken` branch never fires).
Remaining differences are kernel, CPU and contention. The productive next step is
an env-gated heap checker in `alloc_gen.c` plus a CI run with it enabled against
that single test.

**Push patches 14 and 15 into the F\* source.** Requires weakening
`well_formed_heap_part4` to admit infix objects and part2 to admit
interior-pointing fields, then re-proving everything that currently discharges
the infix cases as vacuous (`Allocator.Lemmas.Split`, `Coalesce`, `Sweep`). See
`../PATCHES.md`.

**Separate the OOM signal from corruption.** `new_parent_addr == 0` should not
report a nonsense size request as "major heap full".

**Check the precondition at the boundary.** Nothing verifies `well_formed_heap`
where the bridge calls into the extracted code. A debug-only check there would
have turned bugs 9 and 10 into immediate, local failures instead of corruption
surfacing dozens of collections later.

**Smaller items.** Make's dependency tracking does not know `amd64.o` needs
rebuilding when `domain_state.tbl` changes. The same offset-computation pattern
in the other architectures' `.S` files was left unfixed (amd64-only project).
`ci/expected-failures.txt` was generated locally, so it carries one
platform-flaky entry (`lib-threads/torture.ml`); regenerate it from a CI run once
the tree is green.
